# 产品重新设计：从「岗位列表」到「求职旅程」

## 第一性原理：用户究竟在解决什么问题？

我们一直把这个产品当成"岗位浏览器"，但用户其实在做的是 **「自我管理一段 1-3 个月的求职旅程」**。

求职不是浏览岗位，是一段有阶段的、情绪起伏的、信息密集的、决策连续的过程。

---

## 用户真正的 8 个 Jobs-to-be-done

| # | JTBD | 当前是否解决 | 解决得如何 |
|---|------|-------------|-----------|
| 1 | **发现** — 找到我背景对得上的岗位 | ✓ | 好（爬虫+评分） |
| 2 | **筛选** — 决定哪些值得投 | ✓ | 中（P0/P1/P2/P3 太细，决策模糊） |
| 3 | **投递** — 高效投递并记录 | △ | 差（要手动改状态，会忘） |
| 4 | **追踪** — 知道每个机会进展到哪 | ✓ | 中（有 status，但缺时效感知） |
| 5 | **准备** — 面试前知道复习什么 | ✗ | 没解决 |
| 6 | **复盘** — 从每场面试学到东西 | ✗ | 没解决 |
| 7 | **决策** — 选 offer / 谈薪 | ✗ | 没解决 |
| 8 | **策略** — 知道我整体走到哪一步 | ✗ | 没解决 |

**关键洞察**：当前产品只解决了一半的 JTBD，剩下的 4 个（准备 / 复盘 / 决策 / 策略）才是求职**真正难的部分**——找到岗位是体力活，把每场面试转化成进步才是脑力活。

---

## 重新设计的核心理念

### 旧理念：列表中心（List-centric）
当前结构：
```
导航 → 5 个 Tier 列表
       └─ 每条记录可以编辑状态
```
用户脑子里要回答："这条记录在哪个列表里？" 但用户真正想问的是 **「我现在该干什么？」**

### 新理念：旅程中心（Journey-centric）
新结构按用户**所处的阶段**组织，而不是按数据的属性组织：
```
导航 → 5 个旅程阶段
   1. Today      — 「今天该干什么」
   2. Discover   — 「找新机会 + 快速决策」
   3. Pipeline   — 「我所有在飞行中的机会」
   4. Knowledge  — 「我面试积累了什么」
   5. Decision   — 「我该选哪个 offer」
```

## 五个核心视图

### 1. 🎯 Today（默认首页）

这是用户每天打开工具的第一眼看到的页面。**它直接告诉用户「今天该干什么」**。

```
┌─────────────────────────────────────────┐
│ 早上好，你今天有：                       │
│                                          │
│ ⏰ 1 场面试  · 14:00 某司 二面            │
│   └─ 准备进度 60% → [继续准备]           │
│                                          │
│ 🔥 3 个岗位需要跟进（投了 ≥3 天没动）    │
│   ├─ 某公司A · 投于 5 天前 → [戳 HR]    │
│   ├─ ...                                 │
│                                          │
│ 🆕 12 个新岗位待 triage                  │
│   └─ [开始 triage →]                     │
│                                          │
│ 📝 昨天的反思待补充：某司一面            │
│   └─ [补完反思 →]                        │
└─────────────────────────────────────────┘
```

**只展示需要行动的事**，浏览到位看到的全是 todo。

### 2. 🔍 Discover（快速 triage）

替代当前的「岗位列表」，但用 **swipe 卡片**做单条决策，而不是大列表浏览：

```
┌─────────────────────────────────────────┐
│ ◀ 跳过           ▶ 关注       ▲ 直接投   │
│                                          │
│   [当前一张大卡片]                       │
│   AI平台-算力调度                        │
│   某互联网 · 北京 · 经验不限              │
│   XX-XXK · 20薪                          │
│                                          │
│   匹配度 119                             │
│   命中：AI Infra + Go+K8s + GPU云平台    │
│                                          │
│   JD 摘要...                             │
│                                          │
│   ◀ 跳过   🔖 收藏   ❌ 忽略   ✈ 投   │
└─────────────────────────────────────────┘
```

**Triage 的输出**是给每个岗位打个 **意图标签**：

| 标签 | 含义 | 后续行为 |
|------|------|---------|
| 🎯 目标 | 真想去的，重点准备 | 进入 Pipeline |
| 💪 练手 | 同方向，先投积累经验 | 进入 Pipeline，优先投 |
| 🤔 备选 | 现在不确定，留着观察 | 留在 Discover，定期重看 |
| 🚫 忽略 | 不感兴趣 | 永久隐藏 |

**Triage 一遍后**这堆岗位就分流了，Discover 里只剩下"待决策"的，Pipeline 里有了所有你认领的机会。

### 3. 💼 Pipeline（看板）

替代当前「我的求职」Tab，但用 **Kanban 列**呈现，比列表更直观：

```
┌─────────┬─────────┬─────────┬─────────┬─────────┐
│ 待投递   │ 已投递   │ 沟通中   │ 面试中   │ Offer   │
│  (4)    │  (8)    │  (3)    │  (5)    │  (2)    │
├─────────┼─────────┼─────────┼─────────┼─────────┤
│ 某司AI  │ 某公司A │ 某公司  │ 某司    │ 某某大模型│
│ 🎯目标  │ 💪练手  │ 🎯目标  │ 🎯目标  │ 💪练手   │
│         │ 5天前   │         │ 一面通过 │ 待决策   │
│         │ ⚠跟进   │         │ ▶二面   │         │
│         │         │         │         │         │
└─────────┴─────────┴─────────┴─────────┴─────────┘
```

- **可拖拽流转**：从一列拖到另一列
- **时间感知**：超过阈值会高亮警告
- **意图染色**：练手用蓝色边、目标用绿色边
- **快速操作**：右键卡片打开操作菜单

### 4. 🧠 Knowledge（面试沉淀）

这是当前完全没有的东西。每场面试结束后，结构化记录：

```
┌─────────────────────────────────────────┐
│ 某司 二面 · 容器调度方向                  │
│ 2026-04-08 14:00 · 已通过                │
│                                          │
│ ┌── 被问到的问题 ─────────────────────┐ │
│ │ Q1: K8s informer 工作原理           │ │
│ │     标签：[K8s] [八股]               │ │
│ │     我的答案：✓ 答得不错             │ │
│ │                                      │ │
│ │ Q2: 设计一个 GPU 调度器              │ │
│ │     标签：[系统设计] [GPU]           │ │
│ │     我的答案：✗ 调度策略没讲清       │ │
│ │     → 加入待复习                     │ │
│ └──────────────────────────────────────┘ │
│                                          │
│ ┌── 反思 ─────────────────────────────┐ │
│ │ • 系统设计要先问清约束              │ │
│ │ • 不要急着写代码                    │ │
│ └──────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

**整个 Knowledge Tab 是按知识点聚合的**：
```
[K8s 八股]      共问过 8 次  · 待复习 2 题
[系统设计]      共问过 5 次  · 待复习 3 题
[Go 内存模型]   共问过 3 次  · 都答对
[GPU 调度]      共问过 2 次  · 待复习 1 题
```

下次面试前，看一眼 Knowledge 就知道**重点复习什么**。

### 5. 📊 Decision（决策辅助）

只有手里有 ≥1 个 offer 时才出现。**横向对比 offer**：

```
┌────────────────┬──────────┬──────────┬──────────┐
│                │ 某某大模型│ 某司     │ 某公司   │
├────────────────┼──────────┼──────────┼──────────┤
│ 状态           │ 已 offer │ HR 终面  │ 二面     │
│ Base 月薪      │ XXK      │ XXK      │ ?        │
│ 年包估算       │ XXW      │ XXW      │ ?        │
│ 城市           │ 北京     │ 北京     │ 杭州     │
│ 团队规模       │ 中       │ 大       │ 大       │
│ 技术栈匹配     │ ★★★★    │ ★★★★★   │ ★★★★    │
│ 发展前景       │ ★★★      │ ★★★★    │ ★★★★★   │
│ 我的兴趣       │ ★★★      │ ★★★★★   │ ★★★★    │
└────────────────┴──────────┴──────────┴──────────┘
```

## 数据模型重构

### 旧 Schema
```js
job = {
  ...抓取字段,
  status: '未投递' | '已投递' | ...,  // 单一维度，但混了"我的意图"和"流程进度"
  interviews: [...],
}
```

### 新 Schema（正交化维度）

```js
job = {
  // 抓取字段（不变）
  title, company, salary, area, jd, ...,
  final_score, cluster_hits, ...,

  // 用户意图（你想要这个岗位吗？）
  intent: 'unknown' | 'target' | 'practice' | 'backup' | 'ignored',
  triagedAt: timestamp,

  // 流程阶段（你在这个岗位走到哪一步了？）
  stage: 'discover' | 'pipeline' | 'archive',
  pipelineCol: 'todo' | 'applied' | 'contacting' | 'interviewing' | 'offer' | 'closed',
  appliedAt: timestamp,
  lastTouchAt: timestamp,

  // 终态（仅 archive 用）
  outcome: 'rejected_by_them' | 'rejected_by_me' | 'accepted' | 'ghosted',

  // 面试记录（不变，但加结构化字段）
  interviews: [
    {
      type, time, location, result, notes,
      // 新增
      questions: [
        { q: 'K8s informer 原理', topics: ['K8s'], myAnswer: 'good' | 'bad' | 'unknown', toReview: true }
      ],
      reflection: 'string',
    }
  ],

  // 备注 + 标签
  notes: string,
  myTags: string[],
}
```

**关键变化**：
- `status` 拆成 `intent` + `stage` + `pipelineCol` 三个正交维度
- 每场面试可以挂结构化的 `questions` 列表
- 系统层面有 `Knowledge` 索引（从所有 interviews.questions 聚合而来）

## 重构 vs 渐进 决策

**重构的代价**：
- 当前 build_html.py ~1200 行 HTML 模板
- 重写一次约需要的工作量：~1500 行新代码
- 数据模型迁移：旧 store 自动迁移成新 schema（一段 30 行的迁移代码）

**重构的收益**：
- 完整覆盖 8 个 JTBD（当前只覆盖 4 个）
- 用户体验从"列表浏览器"升级到"求职 OS"
- 长期可维护性大幅提升

**渐进的代价**：
- 在当前混乱的导航上贴功能，越贴越复杂
- 状态机已经是 14 个状态，再加只会更乱
- 旧的"按 tier 浏览"心智模型阻碍新功能

**我的判断**：**全量重构**。当前产品已经验证了核心假设（爬虫+评分+本地存储是可行的），但 UI/数据模型是按"工程师习惯"设计的，不是按"求职用户的真实流程"设计的。现在重构，比未来在 5 个 tab 上贴 10 个功能要值。

## 重构路线图

### Stage 1: 核心数据模型 + 5 个视图骨架（v5.0）
- 新 schema + 旧 store 迁移
- 5 个 view tab：Today / Discover / Pipeline / Knowledge / Decision
- Discover 用 swipe 卡片做 triage
- Pipeline 用 Kanban
- 暂时保留旧的"详细列表"作为 fallback

### Stage 2: 知识沉淀（v5.1）
- 每场面试支持结构化 questions
- Knowledge tab 按 topic 聚合
- 面试前一天的"复习清单"自动生成

### Stage 3: 决策辅助（v5.2）
- Decision 视图实现 offer 对比
- 简历版本管理（review 提到的）
- 基础漏斗分析

### Stage 4: 提醒与回路（v5.3）
- 浏览器通知 / 桌面 Reminder（如果开浏览器）
- 面试 24 小时倒计时
- 反馈回路：用户 👍/👎 评分模型，下次重跑评分自动调权

## 立刻可以做的「最小重构」

如果不想一次推翻重来，我建议至少做这一件事来支撑你的练手 → 目标 流程：

**新增 `intent` 字段**（一天工作量）：
- 每个卡片右上角加意图标签按钮
- 「我的求职」Tab 按 intent 分组
- 顶部加 intent 筛选器
- 不动现有的 status 机制

但坦白说，这只是延迟问题。完整的 Today / Discover / Pipeline / Knowledge 重构才是真正解决问题的方案。
